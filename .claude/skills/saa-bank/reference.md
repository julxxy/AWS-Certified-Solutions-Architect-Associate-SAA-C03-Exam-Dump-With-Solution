# 数据源实况与踩坑记录

每条都对应一次真实翻车。改解析逻辑前先读，别凭直觉调正则。

## PDF 抽取

**pdftotext 本机没装，也不要装。** 纯 `zlib` + `re` 就够，而且效果更好。

PDF 用 **Type3 子集字体 + 十六进制单字节字形码**，几乎没有 `/ToUnicode` 表， 直接读字符串是乱码。但字形编码是 **统一 +0x1C 偏移到 ASCII**：

```python
for chunk in re.findall(rb'stream\r?\n(.*?)endstream', raw, re.S):
    d = zlib.decompress(chunk)  # 2649 流中 2638 个可解压
    if b'BT' not in d or b'Tj' not in d: continue  # 只有 247 个是页面内容流
    for bt in re.finditer(rb'BT(.*?)ET', d, re.S):
        ''.join(chr(int(h, 16) + 0x1C) for h in re.findall(rb'<([0-9A-Fa-f]{2})>\s*Tj', bt.group(1)))
```

偏移后剩 6 个码位要用固定表替换， **连字必须还原**：

| 原码   | 偏移后 | 实际       | 次数 |
|--------|--------|------------|------|
| `0xAC` | `È`    | `fi`       | 1812 |
| `0xAE` | `Ê`    | `ffi`      | 267  |
| `0xAD` | `É`    | `fl`       | 52   |
| `0xAF` | `Ë`    | `ffl`      | 3    |
| `0x9E` | `º`    | `'` U+2019 | 169  |
| `0xA3` | `¿`    | `•` U+2022 | 8    |

漏掉这张表就会得到 `traÊc`、`log les`、`conÈgure` 这种断字。

### 坑 1：`Topic N` 行属于 **下一题**

页面文本顺序是 `Topic 1` → `Question #N` → 题干 → 选项。 按 `Question #` 切块时，`Topic N` 会落到 **上一题**的块尾。

后果：477 题的选项文本变成了 `"Topic 1"`。 做法：遇到 `Topic N` 存为 pending，赋给下一个 `Question #`。

### 坑 2：选项字母独占一行

抽出来长这样，字母和正文 **不在同一行**：

```
A. 
Turn on S3 Transfer Acceleration on the destination S3 bucket. Use multipart
uploads to directly upload site data to the destination S3 bucket.
B. 
```

所以选项行正则是 `(?m)^([A-F])\.[ \t]*$`（要求整行只有字母）， 正文是下一个字母标记之前的全部内容。

### 坑 3：有的选项是图片

477 题的 4 个选项在 PDF 里是 IAM 策略截图， **没有文字**。 不要因为 `text` 为空就丢弃选项 —— 那会让选项数错乱（2831 变 2828）。 保留占位、
`text_en` 留空，构建阶段标 `needs_review`。

### 基准数字（变了就要查）

- 247 个页面内容流，684 题，题号 1–684 连续，页内单调递增， **无跨页断题**
- 选项 **2831** 个（其中 4 个图片型无文字），分布 **ABCD 599 / ABCDE 75 / ABCDEF 10**
- 多选 **86** 题（Choose two 76 / Choose three 10）
- 抽出约 68 万字符

## Solution.txt 切分

### 坑 4：编号列表会伪装成题号 ← 最容易踩

主正则 `(?m)^\s*(\d{1,3})\s*[\].)]\s*` 命中 658/684。但解析正文里有这种东西：

```
1. Real-time Data Stream: To share millions of financial transactions...
2. Data Transformation: ...
3. Scalability: ...
```

它们完全匹配主正则。如果只按「首次出现优先」，这些会被当成题 1/2/3 的重复而跳过 —— 还好。 但如果做了「重复出现就按 prev+1 推断」这类聪明处理，它们会被认成
34/35/36， **把后面几十题的内容整体错位**，而且不报错。

正确做法：主通道要求 **题号单调递增**。

### 坑 5：不要"优化"主正则

试过放宽以兼容 `IMP>>>>>>98.` 前缀，或要求分隔符后必须跟空白 —— 命中数从 658 **暴跌到 509**。主正则保持原样。

要补漏就用 **定点修复通道**：只对缺失的题号做宽松搜索，不动主通道。

```python
r"(?m)^[^\n\d]{0,24}(?<![\d.])%d\s*[\].)]" % n
```

这一招把 `IMP>>>>>>98.` 这类 15 题捞了回来，切分 658 → 673。

### 坑 6：第 315 题被误编号为 `215]`

源文件 typo。文件里 `215]` 出现两次：第一次是真的 215，第二次夹在 314 和 316 之间。

不特判的后果：315 判缺失，且真正的 215 被后面那段覆盖。

做法：位置推断修复通道 —— 缺失的 N，若恰好有一个未占用的匹配落在 pos (N-1) 与 pos (N+1)
之间，就归给 N。这条规则是通用的，不用写死 215。

### 坑 7：191–200 在 txt 里根本不存在

正文从 `190]` 直接跳到 `201]`。PDF 里有完整题干和选项，但永远不会有答案和解析。

处理：保留在题库、`needs_review: true`、排除出题池，但允许「题库」页浏览。 **不要删掉。**

### 最终切分结果

主通道 658 + 前缀修复 15 + 位置修复 1（315）= **674/684**， 缺的 10 个就是不存在的 191–200。

## 答案判定

### 坑 8：答案行可能在很靠后的位置

原先只在 `seg[:400]` 里找多选的第二个字母 —— 655 题的题干超过 400 字符，
`Answers: C) … + E) …` 整行落在窗口外，判成未确定。

做法： **先定位答案行**（含 `ans-` / `Answer(s):` / `Correct answer` 的整行）， **只在这一行里**抽字母。既不受位置影响，也不会被解析正文里的
「Option D 不可扩展」污染。

答案行写法实测有：`ans- xxx`、`ans-xxx`、`Answer: B) xxx`、
`Answers: A) … + C) …`、`Correct answer A: xxx`、以及最常见的 **光一行 `B. 选项原文`**。

### 兜底

行首字母数量恰好等于 `select_count` 时采纳；否则用 `difflib` 把答案句与 每个选项比对， **≥0.65** 才采纳。

### 坑 8b：相似度兜底会给「没有答案的段落」造出答案

源文件里有一批段落只重印了题干 + 全部选项， **一个字的答案都没写**（151/158/159/160/178/179/184/232）。
候选答案句就是选项行本身，于是每个选项与自己的相似度都是 **1.0**，`ranked` 里一大片并列，
`ranked[:select_count]` 取到的纯粹是 Python 稳定排序的产物 —— 却会带着
`confidence 1.0`、`needs_review false` 进出题池。实测 178 被判成 B（Amazon DLM 备份 RDS），
179 判成 B（IAM policy 挂到实例上），全是错的，用户选对反被判错。

做法： **并列就不采纳**。与被取中的最低分并列的选项数超过 `select_count`，直接判 unresolved。
真有答案的题区分度很干净（6 题 0.993 vs 次高 0.302），不会被误伤。
这 8 题的正确答案已进 `data/manual_fixes.json`，每条写了判断依据。

⚠️ 顺带记一条： `_answer_text_candidates` 里取行尾必须 `seg.find("\n", m.end())`，
不能用 `m.start()` —— `_RE_LINE_LETTER` 的 `^\s*` 会跨空行，从 `m.start()` 找会命中
**匹配内部**那个换行符，切出空串被 `len>12` 静默滤掉（721 处匹配丢了 539 处）。
但**别单独修它**：只修切片、不加并列护栏的话，0 题变对，232 题反而从对变错。

当前分布：`regex_letter 626 / manual 9 / fuzzy_match 7 / unresolved 42`。 那 42 道里 10 道是 191–200，其余 32 道是源文件本身就没写答案（很多段落只有一条分隔线）。

## 解析提取

### 坑 9：段落 = 题干 + 答案 + 解析，题干必须剥掉

不剥的话，答完题会把题面原样再显示一遍。而且题干占了长度， 会让「解析过短」的判断全部失真。

两步：

1. 按 PDF 题干文本逐行剥离开头（有些题的答案行没有字母前缀，光找答案行会漏）
2. 再跳过答案行本身

中文段落没有可比对的原文，改用「题干以问句结尾」这个稳定特征：前 10 行里 最后一个以 `？`/`?` 收尾的行即题干末尾。

### 坑 9b：问号后面还有括注

多选题的中文题干长这样：

```
解决方案架构师应采取哪些步骤组合来满足这些要求？（选择两项。）
```

问号**不在行尾**。用 `[？?]\s*$` 会漏掉**所有多选题**的中文题干 ——
实测 `stem_zh` 从 639 掉到 560。正则必须允许尾随括注：

```python
r"[？?]\s*(?:[（(][^）)]*[）)])?\s*$"
```

### 坑 10：跳答案行不能贪心

45 题的解析把答案字母原样重复了一遍：

```
B. Create an Amazon SQS queue, and subscribe it to the SNS topic.
E. Modify the Lambda function to read from an SQS queue.

B. Create an Amazon SQS queue... This will decouple the ingestion workflow...   ← 这是解析
E. Modify the Lambda function... This will allow the Lambda function to...      ← 这也是解析
```

「连续跳过所有像答案的行」会把解析本身也吃掉。 正确做法：答案块 = 从答案行起 **到下一个空行为止**的整段（上限 6 行）。

## 质量标记

### 坑 11：`needs_review` 不能用解析长度当条件

提示词原文把「解析 < 120 字符」列为 `needs_review`。照做的结果是
`needs_review:false` 只剩 **430**，远低于 620 门槛。

原因：源文件里 51–99 等整段区间 **本来就只有题目和答案、没有解析**，实测 254 题如此。

现在的语义拆分：

- `needs_review` —— **只表示答案不可信**，会被排除出考试池与学习出题池
- `explanation_quality` —— `ok` / `thin`(40–120) / `none`(<40)，只进报告，不影响出题

一道答案确凿、只是没解析的题照样能考。当前：可出题 **642**。

## 乱序与字母重映射

**硬性约束：只对 `options` 数组整体 `shuffle`。**
`text_en` 和 `text_zh` 必须作为同一个对象一起搬运。分别洗牌会导致 「英文是 A 的内容、中文是 C 的内容」，双语并排下几乎看不出来。

解析里的字母引用要按本次映射改写， **中英两份都要**。实测出现过的写法：

```
Option C / Options A / Correct answer A: / Answer: B) / 行首 "D. " / "C)"
选项 A / （选项 A）/ 正确答案 A：/ 答案：C)
```

漏掉 `Correct answer A:` 和 `正确答案 A：` 是浏览器实测才发现的 —— 页面上 答案显示 B，解析里却写着「Correct answer A」。

反例（ **不能**误伤）：`A company collects data`、`Amazon EC2 A records`。 所以只在明确的选项引用语境下替换，不做裸字母替换。

### 坑 12：并列字母只改了前一个

`Option A/B`、`Options A, B, and D`、`(A, B)`、`（A、B）`、`选项 A 和 B` —— 这些写法里，
只吃「前缀 + 一个字母」的正则会把后半截原样留下，而它在本次乱序里已经属于**另一个选项**。
651 的解析被改成过 `Option B/B`，172 的 `(A, B)` 只有 B 变了。 **半对半错的引用比完全不替换更难发现。**

做法：前缀之后按「字母 + 连接符 + 字母…」整串匹配再逐个替换，连接符实测有
`/ , 、 & and or 和 与 及 或`；另加一条「括号内只有字母和分隔符」的分支覆盖 `(A, B)`。
连接词都是小写或中文，只替换片段里的 `[A-F]` 不会误伤。改完全库比对：只有 172 / 651 两题
共 4 处（中英各半）行为变化，零误伤。

### 坑 13：R2 只给了部分 `letter_map`

`render_question(..., only_letters=)` 是给 R2 干扰项狙击用的：只展示「正确选项 + 上次错选的那个」。
原先是**先过滤再编号**，于是 `letter_map` 里只有那两三个字母，而 `remap_letters` 是
`mapping.get(L, L)` —— 未展示选项的原始字母原样留在解析里，正好可能等于某个展示项
被重新分配到的新字母。实测：屏幕 A 是正确答案，解析里却写着「Option A is incorrect」，
指的其实是那个没展示的原始 A。1425 个（题 × 干扰项）组合里 106 个中招，中英同时中招。

做法： **`only_letters` 只决定展示哪几个，字母映射必须覆盖全部选项。**
展示项排前面拿 `A、B…`，未展示项排后面拿剩下的字母 —— 解析里对未展示选项的引用会指向
屏幕上不存在的字母（无害），但绝不会误指某个展示项（有害）。前端 R2 屏加一行说明兜住这点。

## 译文

两路来源，别混：

| 路                   | 文件                            | 提供                                      |
|----------------------|---------------------------------|-------------------------------------------|
| A 解析译文（已完成） | `AWS SAA-03 Solution.zh-CN.txt` | `stem_zh`、`explanation_zh`               |
| B 选项译文（待补）   | `data/i18n_zh.jsonl`            | `options[].text_zh`、失真题干的 `stem_zh` |

**重要实测：txt 的题干就是 PDF 题干本身，不是转述。** 逐题 difflib 比对 650 道有效题， 中位相似度 **1.000**，624 题 ≥0.96。所以 `stem_zh` 直接复用路
A， **不需要重译**， 省掉 285K 字符的工作量。只有相似度 <0.9 的 **31** 题需要按 PDF 补译。

⚠️ 算这个相似度必须 `SequenceMatcher(..., autojunk=False)`。difflib 默认对长度 ≥200 的
序列启用启发式：出现频率超过 1% 的元素被当垃圾踢出索引，逐字符比对时空格和常见字母全中招，
匹配块无法成锚。实测 680 题只差 6 处 `fi` 连字，开着 autojunk 算出 **0.145**，关掉是 **0.970**。
开着的时候 <0.9 的题从 31 虚增到 42，多出来的 11 题
（164/301/653/655/657/658/668/671/674/676/680）全是假警报，会白白进补译名单。

路 B 用 JSONL 而不是整体 JSON：写一行是一行，进程被杀不会留下半个非法 JSON， 配合 mtime 热加载可以边译边刷。

### 坑 14：同一份 jsonl，四个加载器四套判据

`build_bank.load_i18n_jsonl` / `app.Bank._overlay_i18n` / `verify_bank` / `i18n_next` 都要读这份文件。
判据一旦不一致，故障方向是**相反**的，两边都很难发现：

| 曾经的不一致                                    | 后果                                                        |
|-------------------------------------------------|-------------------------------------------------------------|
| verify 不跳 `//` 注释行                         | 一行合法注释就让「无坏行」失败、`_fail` 非空、 **基线从此不再更新** |
| verify 把漏写 `letter` 的行当题干条目收下       | build 端判它是坏行丢弃 →译文静默丢失，验证却全绿              |
| `i18n_next.key()` 不做 `.upper()`               | `"letter":"a"` 的行译文其实已生效，`--check` 却报孤儿、退出码 1；进度分母把同一选项数两次 |
| build 的 stem 分支排在相似度分支之后            | 638 道路 A 题干可用的题，jsonl 里的 stem 修订被静默忽略，而 app.py 是无条件覆盖 → 浏览器显示修订稿、questions.json 存旧稿 |

现在 verify 直接复用 `build_bank.load_i18n_jsonl`，`i18n_next.key()` 与之对齐，
build 的 stem 分支把「jsonl 有显式条目」提到最高优先级。 **再加加载器就复用那个函数，别自己抄一份。**

## 一句话记住

数据脏是既定事实。 **能跑 > 功能全 > 数据完美**。 遇到脏数据标记并排除，绝不能让程序报错或让指标静默劣化 —— 后者靠 `verify_bank.py` 的基线对比兜底。
